# Progress note — 2026-08-13

This note records the experimental changes made after the original checked-in 0°–720° forward-roll baseline.

## Baseline that remains the reference

The original repository baseline remains the historical reference for the first unified planner:

- discrete contact sequence: DFS/backtracking;
- continuous support/swing solves: bounded nonlinear least-squares IK;
- touchdown candidates: random joint-space sampling + ground-safe reachability checks;
- finite look-ahead scoring;
- no prescribed gait or switch-angle schedule.

The baseline 720° result and its limitations remain documented in `docs/validated_baseline.md` and `docs/algorithm_solver.md`.

## Experimental algorithm changes after the baseline

The current experiment keeps the same overall architecture but is **not bit-for-bit identical to the baseline implementation**.

The changes used in the experimental runs are:

1. **Analytic 3-DOF leg IK** is used in the fast experimental planner instead of `scipy.optimize.least_squares` for support-foot and touchdown correction.
2. **Progress pruning after a contact switch:** a switch is rejected unless it enables at least one actual next task increment.
3. **Expanded touchdown fallback:** if the normal contact candidates do not solve a subtree, a wider touchdown search is attempted even when normal candidates existed.
4. Search parameters were reduced for the fast experiments (fewer touchdown samples and shorter look-ahead than the original heavy baseline).
5. Task orientation commands were changed from body-following composition to explicit **world-frame rotation axes**.

The discrete search architecture is still:

```text
DFS / backtracking
+
local touchdown generation and contact add/remove ranking
+
continuous per-leg kinematic solves
```

## World-frame task definition

The current task is defined in world coordinates.

### Phase 1 — in-place yaw

For `0 <= s <= 45` deg:

```text
translation: none
rotation: +yaw about world +z
```

\[
R(s)=R_z(s).
\]

### Phase 2 — +x translation with +pitch

For `45 < s <= 525` deg, let `p=s-45`:

```text
translation: +x
rotation: +pitch about world +y
```

\[
R(s)=R_y(p)R_z(45^\circ).
\]

The translation law remains `x = p / 300` m.

### Phase 3 — +y translation with -roll

For `525 < s <= 1005` deg, let `r=s-525`:

```text
translation: +y
rotation: -roll about world +x
```

\[
R(s)=R_x(-r)R_y(480^\circ)R_z(45^\circ).
\]

The translation law remains `y = r / 300` m.

The new rotation is left-multiplied so the commanded axis remains fixed in the world frame rather than rotating with the robot body.

The reusable task definition has been added as `YawPitchRollWorldTask` in `src/lily_contact_planner/tasks.py`.

## Current fresh-search result for the world-frame task

A fresh experimental search from the symmetric initial support set `[0, 2, 4, 6]` reached total progress

\[
255^\circ = 45^\circ\text{ yaw} + 210^\circ\text{ pitch}.
\]

The roll phase was not reached in this partial result.

Headline values:

- success for the partial 0°–255° target: `true`;
- DFS nodes: `7`;
- contact events: `6`;
- final support set: `[0, 1, 7]`;
- stored states: `256` at 1° resolution;
- joint-limit violations: `0`;
- maximum support-foot absolute height error: about `3.89e-16 m`;
- minimum swing-foot height in stored states: about `3.71 mm`;
- minimum body clearance in stored states: about `90.2 mm`;
- body-center projection inside the support region at every stored state: `true`.

This is still a Level-1 kinematic/contact-planning result. It is **not** a dynamics, force/friction, impact, finite-thickness collision, or continuous-time hardware certification.

## Visualization rule for contact switches

The diagnostic GIFs revealed an important visualization requirement: a support leg must not be shown lifting before the replacement foot is shown on the ground.

The current display-only switch reconstruction therefore uses:

```text
pre-switch
-> touchdown approach
-> touchdown complete (old + new support together)
-> support transfer
-> old-foot liftoff
```

This ordering is currently a **visualization reconstruction**, not yet an explicit finite-duration contact-transfer phase optimized by the planner itself.

Likewise, interpolated GIF frames are display-only. They must not be interpreted as planner-produced continuous swing trajectories or as proof that every interpolated configuration satisfies all Level-1 constraints.

## Next technical step

The next planner-level improvement should make touchdown-before-liftoff an explicit hybrid transition rather than only a visualization convention. A later continuous swing-trajectory layer should also impose lift-off/touchdown boundary conditions and dense feasibility checks.
